## Literal published-bootstrap proof

The downloaded tarball was extracted at `package/scripts/frontier-setup.cjs`. From a disposable
project whose `.nvmrc` and `package.json` engine both pinned Node 16.20.2, an absolute Node 16.20.2
executable ran the extracted script with an isolated `HOME` and `XDG_DATA_HOME`:

```sh
/absolute/node-16.20.2 package/scripts/frontier-setup.cjs \
  --version 0.4.0 --node /absolute/node-24.15.0 --apply
```

The literal command exited 0. It printed the absolute selected Node 24.15.0 runtime, exact
`frontier-mcp@0.4.0` pin and declared engine range, immutable installation directory, Cursor user
configuration path, and desired JSON entry. Its internal MCP initialization and `tools/list`
preflight completed before it wrote `/tmp/.../home/.cursor/mcp.json`. The saved `frontier` entry had
a content-addressed absolute launcher path and `args: []`. The Node 16 project gained no
`node_modules` directory.

A second literal invocation without `--apply` also exited 0. It reused the verified installation,
printed the same desired entry, and ended with `Preview only. Add --apply to write this Cursor
entry.` This proves both published quick-start modes against the actual 0.4.0 bootstrap rather than
the source checkout.

did report 2.9.6 before testing stopped.

## Completed npm-launcher evidence

After restoring the locked dependencies with pnpm 10, Bun 1.3.14 passed the full strengthened
runtime check through the exact launcher:

```sh
bun x --bun frontier-mcp@0.4.0
```

The MCP client ran under an absolute Node 24.15.0 executable while Node 16.20.2 was first on
`PATH`. The wrapper supplied as `runtime-check.mjs`'s runtime discarded the installed-entry argument
that the probe appends, then executed the exact npm launcher above. This kept the ordinary probe
unchanged while making the server process use the public package launcher. It passed tools and
resource discovery, create/read and the full claim/release/resolve/reopen lifecycle, nested external
edit invalidation, external Effort creation plus a later edit inside it, four-process claim
exclusion, and four-process id allocation.

Deno 2.9.6 passed those same boundaries only when a one-time registry policy override was added:

```sh
deno run --minimum-dependency-age=0 --no-config --no-lock --node-modules-dir=none --no-prompt \
  --allow-read --allow-write --allow-env npm:frontier-mcp@0.4.0
```

Its wrapper used the same semantics: discard the probe's appended entry and execute the exact `npm:`
launcher. The unchanged command was also tested directly:

```sh
deno run --no-config --no-lock --node-modules-dir=none --no-prompt \
  --allow-read --allow-write --allow-env npm:frontier-mcp@0.4.0
```

The release was published at `2026-09-16T18:43:54Z`. This command ran at approximately
`2026-09-16T22:12:42Z`, when the artifact was about 3 hours, 28 minutes and 48 seconds old, and
exited 1. Its stderr named exact 0.4.0, rejected it under Deno's default 24-hour minimum dependency
age with a cutoff of `2026-09-15T22:12:42.190980Z`, and suggested
`--minimum-dependency-age=0`. A populated `DENO_DIR` did not bypass that check. This was registry-age
behavior rather than a FrontierMCP runtime failure, but the saved launcher must work unchanged
before the tuple is enabled.

The selector therefore enables exact `frontier-mcp@0.4.0` with Bun 1.3.14 on macOS arm64, while
Deno 2.9.6 remains enabled only for 0.3.1. A 0.4.0 Deno project receives a visible Node fallback
because its unchanged command failed during the release verification window. Node is the supported
path for that tuple. A later re-evaluation may expand a future bootstrap, but is outside T92.
