## Question

What quantity gets published as the token claim, measured how, against what — and does it hold up?

The tracker doc already asserts FrontierMCP answers orientation questions "for a fraction of the token
cost of reading every Ticket file". Nothing published backs that. `bench/scan-cost.ts` measures
filesystem scan cost, which is a different quantity from tokens entering a model's context.

Decide the measurement before running it:

- The comparison. Against an agent reading every ticket file, which is the honest baseline for the
  no-server fallback path. Against `gh issue list` and `gh issue view`, which is what a skeptic will
  raise, since Matt's recommended path is GitHub issues. Both, or one, and why.
- The corpus. This repository's own Efforts are real but small and self-selected; `frontier-v1` at 27
  tickets is the largest. Decide what corpus makes the number credible rather than flattering.
- The unit. Tokens into context for a stated task, not bytes on disk and not wall-clock time.
- Whether the number is big enough to publish at all. If a board read saves a modest fraction on a
  realistic effort, the claim quietly drops instead of being stretched — that outcome is a valid
  resolution of this ticket.

If a performance number is also reported, measure the slow end: this machine is faster than the ones
readers will run on, so report the floor rather than caveating a best case.

## Answer

> *This was generated by AI.*

Measured 2026-11-18 on the 2.0.0 source, run in-process, against this repo's nine Efforts (137 Tickets) and the two verbatim legacy fixtures. Counts are `o200k_base` tokens; bytes/4 (what `test/support/tokens.ts` uses) and Anthropic's legacy tokenizer agree within about 10% on Boards and bodies. A current Claude tokenizer was not measured, so absolutes are a floor.

## What holds

**Against reading every Ticket file of the Effort**, one Board is 7.6x to 32.7x cheaper, median 12.2x across 11 Efforts of 3 to 75 Tickets. Workspace-wide, `list_efforts` plus the seven Boards with a non-zero Frontier is 8,817 tokens against 143,615 for every file, 16x.

## What does not

- **A competent grep ties or wins.** `grep -h` over the same nine fields a Board shows costs 0.96x to 1.20x the Board. A four-field grep (`id|title|status|blocked_by`) is 1.8x to 4.7x cheaper than the Board on every schema Effort; filtered to open Tickets it is 2.2x to 39x cheaper. On this repo both narrower greps derived exactly the server's 26 takeable Tickets workspace-wide.
- **Half of a large Board is history.** With no Status filter, 51% of the `frontier-v1` Board (2,728 of 5,351 tokens) is gists of resolved Tickets. [[Tiovvu9]] is the fix already filed.
- **The schemas are not free.** The eight tool schemas are 2,320 tokens in every session (`update_ticket` alone is 810), and the tracker doc is 3,237 more when read. Against reading files the first Board repays that. Against a four-field grep it is never repaid.
- **`gh issue list` is cheaper than a Board** (constructed equivalent, no network: 15 open issues in 619 tokens against a 5,360 Board). It cannot express Edges or takeability; getting those means viewing every open issue, and only there does the server win, at 2.4x.
- **`get_tickets` saves nothing on bodies.** It equals the file.

## Where the Board wins on its own terms

- Prose trackers: on the legacy `telegram` Effort a four-field grep costs 2.6x the Board, because the fields are not in frontmatter.
- Named Tickets: `grep -h` drops the name, which is the filename; the cheapest grep that keeps it is 563 against a Board of 338.
- Cross-Effort Edges: per Effort, the grep could not decide two Tickets and wrongly added one.
- The answer is computed, not derived by the model. The tokens an agent spends reasoning takeability out of grep output, and how often it gets it wrong, were not measured.

## Decision

- **The comparison** is against reading the Effort's Ticket files, stated as such. The grep and `gh` comparisons are reported beside it, not hidden.
- **The unit** is tokens into context to answer "what can I take next in this Effort".
- **The claim**, one sentence: "On eleven Efforts of 3 to 75 Tickets, one Board call told an agent what is open, blocked and takeable for 8 to 33 times fewer tokens than reading the Effort's Ticket files (median 12x)."
- **The caveat that travels with it**: a hand-written grep over the frontmatter returns the same fields for about the same tokens, and the server adds about 2,300 tokens of tool schemas to every session. What the server gives over grep is a computed answer, not fewer tokens.
- **Dropped**: "a fraction of the token cost" unqualified (the tracker doc says this today); any saving against `gh issue list`; any per-session net saving; any saving on bodies; 18x, 24x and 33x as headlines.
- **Corpus**: eleven Efforts, one author. It is a range, not a distribution, and this repo is 71% resolved, which inflates both the file baseline and the Board's gist load. A credible number needs trackers written by other people.

## Corrections to figures already in the repo

The "names cost 45% more" figure (354 against 244) is a bytes/4 artifact. Under real tokenizers it is 338 against 283, about 19%.

## Not measured

A current Claude tokenizer; tool-call framing; what agents without the server actually do (the baselines are constructed, not observed); real `gh` output; cost under prompt caching; deferred tool loading across clients, where schemas may not sit in context at all.

Scripts and raw output were throwaway and are not kept in the repository.
