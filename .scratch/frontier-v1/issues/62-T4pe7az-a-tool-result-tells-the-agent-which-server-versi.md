## Problem

The server version exists only in the MCP handshake (`serverInfo.version`), which the client sees and the agent does not. No tool result carries it.

Capture, 2026-11-13: this repository's `.mcp.json` launched `pnpm dlx frontier-mcp@latest`. pnpm 12 skips releases published under a day ago, so `@latest` resolved to 0.5.0 while npm's latest was 1.0.0 (0.6.0 and 1.0.0 were both too young). The consumer ran a whole session on 0.5.0 believing it was current, and found out only by reading the process list (`ps`) and the pnpm dlx cache directory. Nothing in `list_efforts`, a Board, or a write result could have shown it.

Expected: some ordinary call says what version answered, so behaviour that differs from the docs can be attributed to a stale server rather than debugged.

Workaround taken: inspect the OS process and the package cache by hand.

## Done when

- [ ] An agent can learn the running server version from a tool result, without a client-side resource or handshake API
- [ ] The version shown is the one the handshake reports, from the same single source
- [ ] The cost is one short line at most, on a call an agent makes once per session rather than on every read
- [ ] The tracker doc says where to look

## Agent Brief

**Category:** enhancement
**Summary:** `list_efforts` says which server version answered.

**Current behavior:**
The version is in the MCP handshake only. Confirmed on 2026-11-13: a session ran 0.5.0 under a `@latest` launch and no tool result could show it.

**Desired behavior:**
- Every `list_efforts` result carries the server version, as a short suffix or line beside the `root:` line, for example `frontier-mcp 1.0.0`. This holds in all three shapes of that result: populated, empty `.scratch/`, and no tracker.
- No other tool result changes. A write's `root:` line stays as it is.
- The value is the one the handshake reports, from the same single source.

**Key interfaces:**
- The shared workspace-line rendering, which already owns the handshake version constant
- The `list_efforts` result rendering
- The tracker doc, which should say where to look, and its revision number

**Acceptance criteria:**
The four in the body stand. Add:
- [ ] The version in the result equals `serverInfo.version` from the handshake, asserted in one test
- [ ] The no-tracker result still reads as four lines of guidance, with the version not displacing any of them
- [ ] The added cost is measured in tokens and stated

**Out of scope:**
- Checking the registry for a newer version, or warning about staleness
- The version on any other tool's result
