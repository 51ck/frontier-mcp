## Problem

No tool searches the tracker. "Was this already decided?" and "was this friction filed and since resolved?" are answered today by reading whole Boards.

Capture, 2026-11-13: to check seven new Tickets for duplicates the consumer read three Boards, about 25,000 characters, and matched titles by eye. The research doc measured `get_board` on all eight Efforts at 39,993 bytes, against 13 to 1,045 bytes for a summary-field search result across eleven trial queries.

`answer_gist` and `dropped_reason` are already in the cached scan, so this half of search costs no I/O.

Known limit, to be stated in the output and not hidden: summary fields miss most hits. Measured in the same doc, `search` matched 1 Ticket by title or gist and 17 more by body only; `watcher` 4 and 13. Body search is the Ticket filed alongside this one.

`Tik4z0t` lists filters by kind and Triage role but not by Status. "Resolved Tickets mentioning X" needs one.

## Done when

- [ ] `get_board` accepts `match`, a string or an array of strings; a Ticket hits when any of them occurs, case-insensitive and literal, in its id, title, `answer_gist` or `dropped_reason`
- [ ] No regex, fuzzy or ranked matching; a string with regex metacharacters matches literally
- [ ] `get_board` accepts a Status filter, and it combines with `match` and with `Tik4z0t`'s filters
- [ ] With `effort` omitted the match runs across every Effort, hits grouped under an Effort heading line
- [ ] Resolved and dropped Tickets are searched unless a Status filter excludes them
- [ ] A hit is the Board line unchanged
- [ ] The first line states the terms, the fields searched, the exact hit count, and that bodies were not searched
- [ ] At most 20 hits are rendered, then one line with the exact remainder and the arguments that narrow
- [ ] Order is deterministic, Board order within each Effort; two identical calls over unchanged files return identical text
- [ ] Answered from the cached scan with no file read
- [ ] `get_board` with no `match` is byte-identical to today's
