## Problem

`get_board` takes only `effort` and `root`. There is no call that answers "which Tickets can I take" for a repository, and no way to narrow a Board.

Capture, 2026-11-13, this repository, eight Efforts:

- To find the one takeable build Ticket for an unattended run, the consumer called `list_efforts` and then `get_board` once per Effort with a non-zero `frontier=` count.
- `get_board { effort: "frontier-v1" }` returned about 19,800 characters for 60 Tickets, 58 of them resolved with their gists, to mark one Ticket (`T109`) with `>`.
- The query the work needed was "takeable, `kind: build`, `triage=ready-for-agent`", which is the rule in AGENTS.md User Preferences for overnight shipping. It cannot be expressed; the consumer filters every Board line by eye.
- The same shape repeats for a triage sweep: finding every `needs-triage` Ticket means one Board per Effort.

Expected: one call returning only the lines that decide the next move.

Workaround taken: N+1 calls and manual filtering.

Constraint: eight tools, permanently. This is an optional argument on an existing tool, not a ninth tool.

## Done when

- [ ] One call returns the takeable Tickets of every Effort in the workspace, each line saying which Effort it belongs to
- [ ] A Board can be narrowed to the Frontier only, so resolved and dropped Tickets and their gists are not rendered
- [ ] A Board can be narrowed by kind and by Triage role, and the filters combine

## Agent Brief

**Category:** enhancement
**Summary:** `get_board` reads across every Effort when `effort` is omitted, and narrows by Status, kind and Triage role.

**Argument shape, agreed with the maintainer on 2026-11-13:**
- `effort` becomes optional. Omitted means every Effort in the workspace.
- `status`: optional, one of `open`, `claimed`, `resolved`, `dropped`, or `takeable`. `takeable` is the Frontier filter: exactly the Tickets a full Board marks `>`.
- `kind`: optional, `build` or `decision`.
- `triage`: optional, one of the five roles.
- Filters combine with AND. No other new argument.

**Current behavior:**
`get_board` requires `effort` and returns every Ticket of it. Finding what is takeable across the workspace takes one call per Effort and reading every line.

**Desired behavior:**
- A cross-Effort result groups Ticket lines under one heading line per Effort, in `list_efforts` order, and omits an Effort with no line to show.
- A Ticket line is unchanged from today's Board line.
- A narrowed or cross-Effort result leaves out the Destination or Spec opening, and opens with one line stating the filters applied and the exact count.
- Warnings stay grouped, and only those that bear on a listed Ticket are kept.
- `status` here is a filter value only. `takeable` is not a Status and must not leak into the domain's Status type or into any file.

**Key interfaces:**
- The `get_board` input schema and its description, which is context in every session: keep each new description to one short line
- The Frontier computation, reused as is for `takeable`
- The tracker doc's tool table, and its revision number

**Acceptance criteria:**
The six in the body stand. Add:
- [ ] `get_board {}` with `status: "takeable"`, `kind: "build"`, `triage: "ready-for-agent"` returns exactly the Tickets an overnight run may take
- [ ] An unknown Effort still fails as today; an omitted one never does
- [ ] A filter that matches nothing returns the opening line with a zero count, not an error
- [ ] The added schema cost in tokens is measured and recorded with the read-path measurements

**Out of scope:**
- Text matching (`Tiovvu9`, `T1g1ezn`)

- Any change to `list_efforts`
