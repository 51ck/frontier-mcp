## Problem

A match over summary fields cannot find what is written only in prose, and that is most of it. Measured in the research doc: `search` matched 1 Ticket by title or gist and 17 more by body only; `watcher` 4 and 13; `duplicate` 3 and 10; `token cost` 0 and 5. Reference-shaped queries — a file path, another Ticket's id, `sqlite` — had zero summary hits and 4, 3 and 2 body hits. Nobody writes a file path in a title.

So these stay unanswerable without `grep` over `.scratch/`:

- Which Tickets mention this path, symbol, error string or PR?
- What refers to this Ticket in prose? (Needed before renumbering a duplicate id or dropping a Ticket others cite.)
- Was this decided in an answer whose gist uses a different word?

Cost, measured in the same doc on this repository (116 Tickets, 511KB): walk, read and substring-match every file in 2.71ms median on performance cores and 15.64ms on efficiency cores. It parses nothing, so it is cheaper than a scan. 1000 Tickets is extrapolated, not run.

## Done when

- [ ] `get_board` with `match` and `bodies: true` also matches every Ticket's body, same literal case-insensitive rule
- [ ] Body-only hits are listed after summary-field hits
- [ ] Each body-only hit says which `##` section the first match fell under, and carries whatever the excerpt decision allows
- [ ] The first line reports both counts exactly: summary-field hits and body-only hits
- [ ] The 20-hit cap and exact remainder apply to the whole result
- [ ] The search crosses the seam as its own driver method taking the terms and returning handles with section and excerpt, not as `readTickets` over every handle; the contract pins literal case-insensitive substring so two drivers cannot disagree
- [ ] Files are read fresh on every call and nothing read is cached
- [ ] A Ticket with no parseable fence is searched like any other
- [ ] Cost is measured through the real driver at this repository's size, on the slow cores as well as the fast ones
