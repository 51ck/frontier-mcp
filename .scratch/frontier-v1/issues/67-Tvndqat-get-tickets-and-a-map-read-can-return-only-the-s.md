## Problem

A body read is all or nothing. `get_tickets` takes `ids` and `root`; an `edit_map` read takes `effort`. Neither can be narrowed.

Capture, 2026-11-13:

- `get_tickets` on a long resolved Ticket returns the Problem, the criteria, the full answer and the whole comment log. T99 is the example: its answer records a multi-version Node reproduction. A consumer briefing a builder or checking what is left needs the criteria alone.
- A Map read returns the generated Decisions-so-far block, which gains a line for every resolved Ticket of the Effort. A consumer orienting on an Effort usually needs Destination and the fog list.

No measurement was taken; the size of the waste is asserted, not counted. Lower priority than `Tik4z0t`: bodies are fetched for the few Tickets being worked, Boards on every orientation.

Related: the Ticket-body edit Ticket filed alongside this one names sections by heading; a read filter should name them the same way.

## Done when

- [ ] The saving is measured on this repository's own Tickets and Maps before anything is built, and the Ticket is dropped if it is small
- [ ] `get_tickets` can return only named sections of each Ticket, with the header line always present
- [ ] A Ticket lacking a requested section says so in its own block rather than failing the call
- [ ] A Map read can leave out the generated blocks
- [ ] An unfiltered read is byte-identical to today's

## Agent Brief

**Category:** enhancement
**Summary:** Measure what a partial body read would save; build it only if the saving is real.

**Current behavior:**
`get_tickets` returns the whole body and an `edit_map` read returns the whole Map. No measurement of the waste exists.

**Desired behavior, in two stages. Stop after the first if it fails its gate.**

Stage 1, measure. Against this repository's own `.scratch/`:
- For every resolved Ticket, the bytes of the criteria section alone against the whole `get_tickets` output.
- For every Map, the bytes with and without the generated blocks.
- Report medians and the largest cases, as bytes and as tokens at bytes / 4.

Gate: if a criteria-only read saves less than half of the bytes at the median resolved Ticket, do not build. Record the numbers in a comment, and hand the Ticket back with a recommendation to drop it. Do not drop it yourself.

Stage 2, build, only past the gate:
- `get_tickets` gains `sections`, an array of `##` heading names matched case-insensitively. The header line is always returned. A Ticket lacking a requested section says so in its own block.
- An `edit_map` read gains a way to leave out the generated blocks.
- An unfiltered read is byte-identical to today's.

**Key interfaces:**
- The `get_tickets` and `edit_map` input schemas
- Section names must be the same ones `T1g1ezn` reports for a body hit, so a search result names the argument for the next read

**Acceptance criteria:**
The five in the body stand; the first is Stage 1 and its gate.

**Out of scope:**
- Any edit of a section (`T500woi`)
- Line ranges or byte offsets
