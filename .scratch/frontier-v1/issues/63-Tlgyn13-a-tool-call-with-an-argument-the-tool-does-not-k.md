## Problem

Tool input schemas strip unknown keys. A call carrying an argument the tool does not define succeeds as if the argument had not been passed.

Capture, 2026-11-13, published `frontier-mcp@1.0.0` over stdio:

```
migrate_effort { effort: "demo", rename: true, root: <fixture> }
-> demo: migrated 0
   (nothing to migrate)
```

`rename` was removed in 1.0.0 and is listed in the CHANGELOG as a breaking change ("migrate_effort no longer accepts `rename`"). A caller still passing it gets a success result and no signal that the argument did nothing.

Not tested, inferred from the same mechanism: a misspelled argument on a writer, for example `blockedby` on `update_ticket`, would report `updated` having changed nothing the caller intended.

Expected: an error naming the unknown argument, and nothing written.

Workaround: none available to the caller; the result is indistinguishable from success.

## Done when

- [ ] Every one of the eight tools refuses an unknown top-level argument with an error that names it, and writes nothing
- [ ] The same holds for an unknown key inside a nested object, such as a `create_tickets` ticket entry or an `update_ticket` lifecycle object
- [ ] `migrate_effort { rename: true }` fails, and the message says `rename` is not an argument
- [ ] Pinned by a test through the harness for each tool
- [ ] The misspelled-writer case above is checked for real and the result recorded here

## Agent Brief

**Category:** bug
**Summary:** Every tool refuses an argument it does not define, at any depth, and writes nothing.

**Verification (2026-11-13, published `frontier-mcp@1.0.0` over stdio, fixture repo).** The case the body marks as inferred was run, and it is worse than filed:

- `update_ticket { id, resolve: { answer_gist: "x", anwser: "long answer" } }` returned `T1 updated`, `status=resolved`. The answer was discarded; the file has the gist and no answer.
- `create_tickets` with a ticket entry `{ title, blockedby: ["T1"], triag: "wontfix" }` returned `1 created`. The file has `blocked_by: []` and no Triage role.
- `update_ticket { id, blockedby: ["T999"] }` alone failed, but only by accident: with the unknown key stripped nothing was left, so the "Nothing to do" check fired. Beside any valid argument it would have succeeded.
- `migrate_effort { effort, rename: true }` succeeded, as the body records.

**Current behavior:**
Tool input schemas strip unknown keys at the top level and inside nested objects. A misspelled or removed argument is indistinguishable from one never passed.

**Desired behavior:**
A call carrying a key the tool's schema does not define fails before anything is read or written, with a message naming the key and, for a nested one, where it sits. Applies to all eight tools.

**Key interfaces:**
- The eight tool input schemas, including nested objects: the `update_ticket` lifecycle objects (`claim`, `resolve`, `drop`, `reopen`) and each `create_tickets` ticket entry
- The published JSON Schema for each tool should say the same thing the validator enforces (`additionalProperties: false`), so a client can catch it too

**Acceptance criteria:**
- [ ] Each of the eight tools refuses an unknown top-level argument, names it, and writes nothing
- [ ] An unknown key inside a nested object is refused the same way
- [ ] The three verified cases above each fail, and the fixture file is byte-identical afterwards
- [ ] `migrate_effort { rename: true }` fails and the message names `rename`
- [ ] The emitted tool schemas declare no additional properties, pinned beside the existing annotation pins
- [ ] A harness test per tool
- [ ] The CHANGELOG entry marks it as a breaking change for callers that pass stray keys

**Out of scope:**
- Suggesting the nearest valid argument name
- Any change to which arguments exist
