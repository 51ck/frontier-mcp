## Question

`resolveWorkspace` takes the workspace from an explicit `root` argument first, then `FRONTIER_ROOT`, then the working directory walked upward to a root marker (`src/workspace.ts:34-46`). `root` is a **per-call** argument, so one server process serves any number of workspaces without restarting, and the comment at `:41` states this as intent rather than accident — a client that moves to another worktree retargets a call rather than relaunching.

That model has never been argued on its own. It has been leaned on: [[T54]] used exactly this cardinality to kill the environment variable and the server argument as homes for the repo's id pattern, on the ground that one process-wide slot cannot answer a per-workspace question. The reasoning is sound and the conclusion is probably right, but a load-bearing property deserves a Ticket of its own rather than a supporting role in someone else's.

Three consequences worth arguing.

**Drivers accumulate and nothing evicts them.** `createDriverRegistry` (`src/driver-registry.ts:16-33`) keeps a `Map` from root to driver, creates on miss, and clears only in `closeAll()`. Each driver holds its own scan cache, its own write queue, and its own `fs.watch` on the storage directory (`src/storage/markdown/driver.ts:157`). A long-lived session that touches many workspaces therefore holds a watcher per workspace for the life of the process. Whether that is a real cost or a theoretical one is measurable, and this Effort already has the habit of measuring before deciding.

**Any directory on the machine is reachable.** `requireDirectory` checks only that the path resolves to a directory (`workspace.ts:92-97`); nothing constrains `root` to the session's own tree, and a workspace with no `.scratch/` is explicitly supported as "a fresh project" (`:50`). So a client that can call a tool can point the server at any directory the process can read. That may be exactly right for a local stdio server, and it is a different proposition over any other transport, which `frontier-web` will meet.

**MCP Roots was ruled out and the reason should be re-read, not re-argued.** `workspace.ts:44-47` records that Roots is deprecated as of protocol revision `2026-07-28` (SEP-2577), which directs implementations to pass directories through tool parameters or server configuration instead. That is the strongest single argument for the current design; this Ticket should confirm the citation still holds rather than reopen it.

This sits beside T29 rather than under it. T29 asks whether *separate processes* should share one driver; this asks what *one process* serving many workspaces already commits us to. Neither gates the other.

## Acceptance criteria

- [x] Whether per-call `root` stays the workspace model is decided, with the SEP-2577 citation re-verified
- [x] The unbounded driver registry is ruled on — evict, cap, or accept, with the reason stated

## Answer

> *This was generated by AI.*

Evidence gathered 2026-11-18 on an Apple M4 Pro, macOS, Node 24.15.0; Linux figures are from libuv and kernel source, not measured.

## 1. Per-call `root` stays

SEP-2577 re-verified against the 2026-07-28 changelog, the Roots page, the deprecation registry and the SEP text (Status: Final). Roots is **deprecated, not removed**: functional until the first revision on or after 2027-07-28. The same revision removes `notifications/roots/list_changed`, so Roots could no longer follow a client that changes directory mid-session, which is the case per-call `root` exists for.

The comment in `src/workspace.ts` overstates it in three ways and should be corrected: the changelog says "suggested migrations", not a directive; the list also names resource URIs; and it should say deprecated rather than imply gone.

The objection considered: server configuration is equally blessed, so `FRONTIER_ROOT` alone would comply, and the argument costs schema tokens on all eight tools. It loses because a process-wide slot cannot follow a session that moves between worktrees.

## 2. The registry stays unbounded

Measured with 1, 10, 50 and 200 workspaces, each a full copy of this repo's `.scratch/` (137 Tickets):

- **File descriptors: none.** The count stayed at 11 at every N; libuv multiplexes every watch onto one FSEvents stream.
- **Heap: about 1.4MB per driver while a scan is cached, about nothing once it is dropped.** The watcher's settle schedule drops the scan within a second of attach, so a workspace touched once retains roughly nothing.
- **Nothing failed at 200**, also with `ulimit -n` at 256.
- **Ceilings are far off**: 4096 recursive watches per process on macOS; on Linux one watch per directory (19 for this repo's shape), so the 8192 `max_user_watches` floor is about 431 workspaces, shared with the user's other watchers.

No eviction and no cap. Eviction would add attach and detach churn, and attach is where an event was measured lost (below).

## 3. What constrains `root`

On stdio, nothing beyond "an existing directory", and that stays: the process already has the user's filesystem rights, a read creates nothing, and a write to a directory with no tracker needs `create: true` and lands only under `<root>/.scratch/`. A prompt-injected agent can still plant markdown under `.scratch/` in any writable directory; that is accepted for a local stdio server and recorded here as accepted, not overlooked.

**For any other transport `root` must be confined to configured directories or removed.** Flagged for `frontier-web` ([[T26]]).

`root` never walks upward to a marker; only the working directory does. A `root` of `repo/packages/app` is served as its own workspace and a create writes `repo/packages/app/.scratch/`. Left as is: an explicit argument means what it says.

## 4. T54

Its reasoning stands and its subject is gone. [[T54]] used this cardinality to rule out a process-wide home for the id pattern; ADR 0008 removed the pattern, and no per-workspace setting exists today. The rule survives as a constraint on any future repo-level setting: it lives in the storage directory, never in the environment or a server argument.

## Defects found, filed separately

- **The registry keys on the path as spelled.** `repo`, a symlink to it, and `REPO` on a case-insensitive volume built three drivers for one directory, each with its own cache, watcher and write queue. Two concurrent writes through two spellings did not lose data in 40 rounds, but only because the revision guard held; the per-workspace write queue the contract promises was not what serialized them.
- **A watcher that fails goes silently stale.** At 4097 watches every watch in the process emits `EMFILE`; the handler closes the watcher and nothing re-attaches. On Linux a failed `watch()` on one directory is swallowed. Either way the Board serves a stale scan with no warning.
- **Attaching a new workspace can drop an event on an existing one**: 2 of 48 writes landing at the instant of another driver's attach were not seen within 800ms; none at 1ms or later. libuv rebuilds the stream on every handle add, and the settle invalidations cover only the new watch. Small sample.
- The ignored-`frontier.yml` warning is computed once at driver construction, so deleting the file does not clear it until the server restarts. Read from code, not demonstrated.
