## What to build

An agent can attach metadata the schema does not know about. `create_tickets` and `update_ticket` take an `extra` object; every extra field is visible on read and survives every later update.

- An update replaces only the top-level `extra` keys it supplies. There is no deep merge: a supplied key's value replaces the stored one whole, and keys not supplied are untouched.
- Removal is by an explicit list of keys, reusing `drop_keys` where it fits.
- A known field cannot be set through `extra`: `extra: { status: ... }` is refused, not written.

This builds on what [[T102]] and [[T103]] made for keys outside the schema: shown by `get_tickets`, preserved by writes, removed by `drop_keys`. Open, and to be stated by the build rather than assumed: whether an extra field is stored as a top-level frontmatter key or under one key, and whether "Unimported key" survives as a term once such keys can be written on purpose.

Filtering by extra fields is tracked in `frontier-search`.

## Acceptance criteria

- [ ] `create_tickets` with `extra` writes those fields, and `get_tickets` shows them
- [ ] `update_ticket` with `extra: { a: 1 }` on a Ticket holding `a` and `b` leaves `b` byte-identical
- [ ] A nested value is replaced whole, not merged; a test pins it
- [ ] A listed key is removed, and removing an absent key fails the call as `drop_keys` does today
- [ ] An `extra` key that is a schema field, or the marker, is refused, naming the field and the argument that sets it
- [ ] An update that touches no extra field leaves every extra field byte-identical
- [ ] Extra fields never affect Status, Edges or the Frontier
- [ ] The rule that a write never reformats what it did not touch still holds for the untouched keys
- [ ] The tracker doc and glossary state where extra fields live and how they are named; the doc's revision is raised

Owner's decisions of 2026-11-18. They amend this Ticket and supersede the body where the two disagree, including the body's "open" paragraph on where an extra field is stored.

**Storage, settled.** Additional metadata lives at the top level of the frontmatter. `extra` is the argument envelope of the MCP call, not a persisted key: no nested `extra:` object is ever written.

**Reserved fields, settled.** Every schema-owned field and `id` are reserved. Existing `id` semantics and support are unchanged; `id` is simply not reachable through this route. An earlier suggestion to permit `id` via `extra` is withdrawn.
