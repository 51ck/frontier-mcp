## What to build

The tool slot `migrate_effort` held is given to a check, provisionally named `check_tracker`. An agent calls it to learn how to write a Ticket and to find out what is wrong with the files that are there. It returns:

- the current Ticket frontmatter schema,
- the layout contract, with its version: supported paths, the role of each file, known unsupported placements,
- a valid example Ticket,
- file diagnostics for the workspace: malformed marked Tickets and known unsupported placements, each with file, field and expected.

All four are derived from the same authoritative rules validation uses, so the tool cannot describe a contract the server does not enforce. The tool surface stays at eight. The name is provisional.

## Acceptance criteria

- [ ] `migrate_effort` is gone and the surface is still eight tools
- [ ] The schema, layout contract and example come from the one definition the validator reads; a test fails if any of them is edited apart from it
- [ ] The example Ticket the tool returns passes validation
- [ ] The layout contract carries a version, and the tool states it
- [ ] Every diagnostic `explicit-ticket-marker` can raise is itemized here with file, field and expected, where the Board only groups them
- [ ] A clean workspace returns the contract and says there is nothing to fix
- [ ] The call reads only supported locations
- [ ] The tool's schema cost in tokens is measured against `migrate_effort`'s and recorded with the read-path measurements
- [ ] The tracker doc's layout and frontmatter sections are generated from, or pinned by test to, the same definition; its revision is raised
- [ ] The tool states its side effects as the other readers do (`test/ship.test.ts`)
