> *This was generated by AI during triage.*

**Category:** enhancement

**Summary:** New Tickets carry no sort-order prefix, so the Board needs an order that does not depend on one.

**Current behavior:** A Board lists Tickets by the `NN` prefix of their filenames.

**Desired behavior:** A Board lists Tickets so that a Ticket never appears above one it is blocked by within the same Effort. Ties break by the filename's numeric prefix where a file has one, then by name. A cycle already in the workspace does not break the listing; its members fall back to the tie-break order. The order is stable: the same files give the same Board.

**Key interfaces:** the Board renderer's ordering; the summary field that carries the prefix.

**Acceptance criteria:**

- [x] In an Effort of unprefixed Tickets, every blocker is listed above its dependents
- [x] An Effort of prefixed Tickets whose Edges agree with the prefixes lists exactly as it does today
- [x] A mixed Effort is deterministic across repeated reads and across a restart
- [x] A hand-made cycle still produces a full Board

**Out of scope:** storing an order; any change to `list_efforts`.

## Answer

Built on `feat/ticket-names`. 545 tests and `pnpm run check` pass.

- **Order:** stable topological, always the smallest free Ticket by the tie-break. Cross-Effort, dangling and duplicated-name Edges impose none. When nothing is free, the smallest Ticket that is itself on a cycle is listed and the walk continues, so a Ticket downstream of a cycle stays below its blocker.
- **Cost:** heap plus blocker counts. 1000 Tickets: 0.13–0.84ms on performance cores, 0.36–2.23ms under `taskpolicy -b`. The first version was quadratic (up to 76ms at 1000 on a slow core) and was rewritten after review.
- **`TicketSummary.order` became `orderHint`**, absent when the file has no prefix. Nothing depends on directory enumeration order any more.
- **A prefix is digits then a hyphen.** `2fa.md` is the Ticket `2fa` with no hint; before, it read as order 2.
- **Other listings** (scan order, the Map's generated blocks, the `migrate_effort` report) use the tie-break alone, not the topological order: the scan order must not depend on Edges, and Decisions-so-far would otherwise be rewritten whenever an Edge is added. In a mixed Effort the next resolve does rewrite that block once, prefixed Tickets first.
- **One visible change for existing workspaces:** where an Edge points at a higher-numbered Ticket, the Edge now wins over the prefix.
- A bare sort-order Edge such as `01` resolves only to a file that carries that prefix, never to one that merely sat first in the directory.
