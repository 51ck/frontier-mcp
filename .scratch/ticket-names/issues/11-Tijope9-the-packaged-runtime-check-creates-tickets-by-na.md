**Category:** bug

**Summary:** The script CI runs against the packed tarball still drives the 1.x creation contract, so every package-runtime leg fails on the 2.0 branch.

**Current behavior:** The runtime check calls `create_tickets` without `name`, asserts the created id matches `^T[0-9a-z]{6}$`, and its cross-process section writes `id_pattern: T<N>` and asserts every created file carries `id:` under a counter guard. Since `create_tickets` began requiring `name`, the script throws at its first creation. The scripts contract document still describes minting and pinning `id_pattern`. Found by the review of the migration slice on 2026-11-15; reproduced by running the script.

**Desired behavior:**

- The check creates Tickets by name and asserts what 2.0 promises: the file at the path the name implies, no `id` field, the Ticket readable and updatable by its name.
- Its cross-process section asserts the guarantee that replaced the counter: several processes creating the same name at once leave exactly one file and the rest are refused, with no guard file left behind.
- Nothing in it sets or depends on `id_pattern`.
- The scripts contract document describes the same checks.
- All nine package-runtime legs of the runtime workflow pass on the branch.

**Key interfaces:** the packaged-runtime check script and the scripts contract document; the runtime workflow's package jobs, which must stay blocked by the development job as they are.

**Acceptance criteria:**

- [ ] The runtime check passes locally against a freshly packed tarball on the development Node
- [ ] It contains no reference to a minted id shape, a counter guard or `id_pattern`
- [ ] The cross-process assertion fails when run against a build whose creation is not exclusive
- [ ] The scripts contract document matches the script

**Out of scope:** the setup matrix and installer scripts, unless they call the creation contract too; if they do, say so on this Ticket.
